# Расчеты и алгоритмы по коду

## Числа и нормы

`Rules.Parse` принимает запятую или точку как десятичный разделитель, не принимает
разделители тысяч, NaN или Infinity. `Rules.Number` проверяет диапазон и точность.
Физические decimal хранятся масштабированными INTEGER; все вычисления — decimal.
`Rules.Money` округляет после суммирования до двух знаков AwayFromZero; MoneyConverter
используется для денежных итогов таблиц. Показатели питания отображаются с 1–2 знаками.

`NutritionCalculator.Calculate` получает проверенный ProfileInput:

```text
BMR = 10 * кг + 6,25 * см - 5 * возраст + (5 для Male, -161 для Female)
K = BMR * {1,2; 1,375; 1,55; 1,725; 1,9}
Б = K * 0,30 / 4; Ж = K * 0,30 / 9; У = K * 0,40 / 4
```

При ручной цели для плана применяется FromCalories. Цель K и производные БЖУ
нормализуются до 8 знаков при записи плана. Генератор проверяет сохраненное K,
а не округленное представление строки UI. Профиль обязателен и для ручной цели.
Эталон N1: 1698,75 BMR; 2633,0625 ккал; 197,4796875 / 87,76875 / 263,30625 г.

`RecipeCalculator.Calculate`: сумма по ингредиентам `q/100 * значениеНа100г`
для ккал, БЖУ и цены. Рецепт — одна порция. Snapshot копирует название/категорию
продукта, граммы, питание и цену; Meal также копирует название и инструкцию рецепта.
Эталон N2: 500 ккал; Б19, Ж13,4, У77,4; 0,70 BYN.

## FEFO

`PantryAllocator.Allocate` получает копии Lot, агрегированные Requirement и дату.
Партии сортируются по Expiry (null последним), затем Id. Используются только
партии с Expiry >= date либо без срока. Для каждого продукта берется min(нужно,
остаток партии); недостаток возвращается отдельно. Входные Lot неизменяемы.
Результат содержит новые остатки и дефицит; ни списаний в БД, ни отрицательных остатков нет.

Эталон N4: 100 г до 02.11 и 150 г до 10.11; потребности 80 г на 02.11 и 200 г на 03.11.
Распределено 230 г, дефицит 50 г, по цене 0,40 — 0,20 BYN. Реальные партии не меняются.

## Генератор

`MenuGenerator.Generate` получает неделю, today, K, B, рецепты со значениями
продуктов, исключения, партии, MaxVisitedNodes, CancellationToken. Доступа к БД нет.
Кандидаты фильтруются по MealType и исключениям; КБЖУ и потребность вычисляются один раз.

Слоты: день1 Breakfast/Lunch/Dinner, затем остальные дни до 21 записи. В каждой
ветви хранятся накопленная стоимость, калории текущего дня, число использований
рецептов и виртуальные партии. Кандидаты сортируются по убыванию обеспеченности
по весу пригодными запасами на max(today,date), затем по меньшему числу повторов,
близости к 30/40/30% K, цене и RecipeId.

Попытка добавить кандидата считается одним узлом. До попытки проверяется лимит:
ровно N попыток максимум, включая N=0. Превышение бюджета/верхних калорий,
недобор после Dinner и безопасная нижняя оценка стоимости оставшихся слотов
отсекают ветку. Виртуальные партии распределяются через FEFO, а нехватка не запрещает
рецепт. При неудаче удаляется последний выбор, уменьшается счетчик использования,
родительская копия партий сохраняется. Это возврат по дереву решений.

Дневные условия включительны: `0,9K <= ккал <= 1,1K`; неделя `стоимость <= B`.
Бюджет включает имеющиеся дома продукты. Повторы разрешены, строгих границ БЖУ нет.
NoCandidates означает отсутствие допустимой категории, NoSolution — исчерпанное
дерево, SearchLimitReached — только исчерпанный лимит; Cancelled отличается от них.
По умолчанию 100000 узлов; каталог не урезается до первых рецептов.

`HomeMenuService.GenerateWeekAsync`: под Gate загружает входной снимок, SessionTicket,
Revision, локальную дату и текущий Version. Поиск выполняется Task.Run без транзакции.
Перед записью повторно проверяются отмена, ticket, Revision, дата, Version и отсутствие
приготовлений. 21 запись и итоговые ограничения проверяются еще раз. Удаление старого
содержимого и запись нового входят в одну транзакцию Write. Revision растет после commit.
Отмена/ошибка до commit не изменяет неделю. После commit операция считается сохраненной
и UI перечитывает фактические данные; поздняя отмена уже не откатывает запись.

## Ручная замена

`ReplaceMealAsync` проверяет владельца/Version/CookedAtUtc, соответствие категории,
объединение текущих и сохраненных исключений. Рассчитывает новый снимок и
PlanAnalysis.Warnings. При нарушении K/B и отсутствии согласия возвращает
ConfirmationRequiredException; транзакция откатывается до диалога.
Подтверждение вызывает новую операцию с тем же Version и повторными проверками.
ConfirmationRequiredException возвращает Revision; acceptViolations для нарушающей
замены требует эту же ревизию. Изменения рецепта, цены, исключений или иных входов
после показа расчетов отклоняют устаревшее согласие.
Старые снимки удаляются, новые вставляются атомарно, Version увеличивается.
Исключения и приготовленность нельзя обойти согласием на нарушение бюджета.

## Приготовление

`MainViewModel.CookAsync` показывает дату/блюдо/граммы и получает подтверждение.
Отказ вообще не вызывает CookMealAsync. Сервис под Gate открывает транзакцию,
проверяет владельца, Version, CookedAtUtc==null, date<=today и исключения.
Потребность берется из исторических снимков, годность — на сегодня.
FEFO вычисляется для всех продуктов до изменения любой партии.
Любой дефицит возвращает названия и недостающие граммы без записи.
При полном обеспечении обновляются партии, CookedAtUtc=Clock.GetUtcNow и Version.
SaveChanges/commit фиксируют все совместно. При ошибке — rollback; повтор и конкурентный
повтор запрещены. Нулевые партии сохраняются. Перегенерация недели с приготовлением запрещена.

## Покупки и статистика

`Shopping` сортирует неприготовленные записи по Date/MealType/Id. Для каждой берет
max(today,date), распределяет виртуальные FEFO-партии и передает остаток следующей.
Требуемые, покрытые и недостающие граммы суммируются по ProductId. Выводятся строки
с положительным дефицитом, по текущей категории/имени, с текущей ценой Product.
Просмотр не меняет БД, не резервирует остатки для других недель и не пополняет холодильник.

`GetWeekSummaryAsync` считает плановые КБЖУ по дням/неделе и цену из снимков,
дневные отклонения от целей, `Budget - menuCost`, стоимость покупок отдельно,
количество и КБЖУ подтвержденных блюд. Это учет подтверждений, а не физиологические
измерения; дата фактического приготовления хранится отдельно от даты плана.
