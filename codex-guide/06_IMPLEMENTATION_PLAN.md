# Порядок реализации

## Шаг 1 Осмотр и фиксация решений

Прочитать локальные инструкции и гайд. Проверить `git status`, содержимое solution/csproj, версию SDK, существующие зависимости и работоспособный код. Не перезаписывать чужие незакоммиченные изменения. Кратко записать в `docs/report/DECISIONS.md` исходное состояние, выбранную структуру, хранение чисел, состояние Windows-проверки и отличия от предложенных имен.

Из первой работы взять .NET 8, C# 12, EF Core 8.0.10 как исходную версию. Для нового проекта допустимо выбрать проверенный доступный исправляющий выпуск **8.0.x**, синхронно для пакетов EF/Design/Tools и dotnet-ef, с записью точного номера и причины. Не использовать wildcard или автоматически последний major. Точные итоговые версии зафиксировать в csproj/централизованных зависимостях и VERSIONS.md. Старую строку «8.0.10» в будущем отчете исправить, если выбрана другая версия.

Сохранить Visual Studio 2022. Для net8.0 нужен VS не ниже 17.8, а для конкретного SDK требования могут быть выше: проверить совместимость установленного SDK. Если создается `global.json`, указывать реально доступную совместимую версию и понятный rollForward, а не выдуманный номер. Для хеширования использовать библиотечный PasswordHasher<User>; он не требует создания веб-приложения. Зафиксировать режим/параметры используемой версии, не копировать параметры ПВЗ как якобы существующие.

## Шаг 2 Домен и расчеты

Создать Core, перечисления, DTO и сервисные контракты. Реализовать валидаторы, NutritionCalculator, RecipeCalculator, FEFO-распределение и чистый MenuGenerator. Сразу проверить числовые примеры из 07_ACCEPTANCE.md: они закрепляют смысл до подключения UI.

Разделить результаты поиска на Success/NoCandidates/NoSolution/SearchLimitReached/Cancelled либо эквивалентные типы. Не возвращать пустой список как универсальный ответ на все причины.

## Шаг 3 Хранилище

Создать Infrastructure, AppDbContext и конфигурации сущностей. Внести начальную миграцию и snapshot в репозиторий. Реализовать фабрику контекста, блокировку экземпляра, сериализацию записей, инициализацию и seed. Интеграционные проверки запускать на отдельных SQLite-файлах с миграциями. EF InMemory не проверяет ограничения SQLite и для этих сценариев не подходит.

Для начального seed добавить не менее 15 продуктов и 9 рецептов (по 3 каждого приема пищи), с понятными ингредиентами и учебными ценами. Не выдавать seed за актуальный прайс магазина или официальную пищевую базу. Пользователей и их пароли в рабочем seed не создавать. Отдельные синтетические фикстуры для алгоритмов допустимы только в тестах.

Подготовить демонстрационный сценарий с проверенной комбинацией цели, бюджета и каталога, для которой генерация заканчивается успешно. Не подменять для этого результат генератора заранее сохраненной сеткой.

## Шаг 4 Бизнес-сервисы

Реализовать регистрацию, вход, сеанс, профиль, общие каталоги, партии, исключения, меню, покупки и статистику. Все приватные операции проверяют владельца. Сначала обеспечить транзакции, отказ при нехватке и повторном приготовлении, затем подключать команды UI.

У генерации отделить загрузку входного снимка, чистый поиск и атомарное сохранение. Изменившиеся во время поиска данные не должны приводить к молчаливой записи устаревшего результата. Сохранить старый план при любой неудаче.

## Шаг 5 WPF

Реализовать все экраны из 05_UI.md. Проверить binding errors, жизненный цикл контекстов, команд и диалогов. Справочники, редактирование, расчет и списание должны работать через настоящий сервисный слой. Пустые панели «в разработке» не считаются выполненными функциями.

Долгий алгоритм запускать в фоне над чистыми данными. Не передавать живые EF-сущности с отслеживанием между потоками. После завершения возвращаться в UI-поток для обновления коллекций. Работа с SQLite остается короткой; вызов Async сам по себе не гарантирует, что провайдер не блокирует вызывающий поток.

## Шаг 6 Проверки и демонстрация

Создать meaningful unit/integration tests для расчетов и существенных бизнес-правил. Не писать десятки проверок геттеров и конструкторов. Пройти сценарии 07_ACCEPTANCE.md, результаты записать с фактическими командами, платформой и статусами. На Windows отдельно проверить запуск и полный пользовательский маршрут.

Для нового решения базовые команды из корня:

```powershell
dotnet --info
dotnet restore HomeMenu.sln
dotnet build HomeMenu.sln -c Release --no-restore
dotnet test tests/HomeMenu.Tests/HomeMenu.Tests.csproj -c Release
dotnet run --project src/HomeMenu.Wpf/HomeMenu.Wpf.csproj
```

Для EF использовать local tool manifest с согласованной версией dotnet-ef. Миграции можно создавать с Infrastructure как проектом и фабрикой design-time без запуска WPF; точную проверенную команду записать в README. Пример структуры команды, требующий адаптации к фактическому проекту:

```powershell
dotnet tool restore
dotnet ef migrations list --project src/HomeMenu.Infrastructure --startup-project src/HomeMenu.Infrastructure
```

На Linux/macOS доступны тесты Core/Infrastructure. Сборка WPF с `-p:EnableWindowsTargeting=true` допустима как проверка компиляции при наличии пакетов, но не как проверка запуска. В неподходящей среде не устанавливать вымышленный статус «приложение протестировано». При необходимости добавить Windows CI, который делает restore/build/test; автоматическую проверку окон не утверждать, если ее нет.

## Шаг 7 Документация для отчета

Обновить README запуска, `docs/report/` и диаграммы по **фактическому** коду. Состав файлов указан в 08_REPORT_CONTRACT.md. Провести обратную проверку: каждое утверждение о реализации должно иметь путь/символ/тест или явную отметку, что оно пока не подтверждено. Устранить оставшиеся расхождения, заполнить итоговую передачу.

Не добавлять в git bin/obj, рабочие *.db и журналы SQLite, локальные пароли, приватные профили, временные выгрузки. Учебные JSON-справочники, миграции, тестовые фикстуры, исходники схем и настоящие неперсональные скриншоты допустимы. Локальный README должен позволять третьему лицу собрать проект после чистого клонирования.
