# Проверки и критерии приемки

Таблица описывает необходимые проверки, а не их результаты. Codex реализует автоматические проверки существенных правил, ручные сценарии проходит на доступной платформе и фиксирует фактические статусы. `Blocked/NotRun` нельзя заменять на `Passed`.

## Числовые эталоны

### N1 Профиль

Мужчина, 20 лет, 70 кг, 175 см, активность 1.55:

```
BMR = 1698.75
K = 2633.0625
P = 197.4796875 г
F = 87.76875 г
C = 263.30625 г
```

При показе K до двух знаков получится 2633.06, но расчеты не должны брать округленную строку UI. Сохраненные цели плана нормализуются до 8 знаков, как описано в модели. Для женщины с теми же данными BMR = 1532.75, K = 2375.7625. Проверить каждый коэффициент активности и отказ на невалидном возрасте/весе.

### N2 Порция

Учебные продукты, показатели на 100 г:

| Продукт | Ккал | Б | Ж | У | BYN |
| --- | --- | --- | --- | --- | --- |
| Овсяные хлопья | 380 | 13 | 7 | 68 | 0.40 |
| Молоко | 60 | 3 | 3.2 | 4.7 | 0.15 |

Рецепт: хлопья 100 г + молоко 200 г. Итог: **500 ккал; Б 19 г; Ж 13.4 г; У 77.4 г; цена 0.70 BYN**. Для ручного округления денег также проверить случай, когда сумма точных строк отличается от суммы округленных строк.

### N3 Генератор на синтетической фикстуре

Один тестовый продукт: 200 ккал, Б 15, Ж 6.67, У 20 на 100 г, цена 0.20 BYN/100 г. Три рецепта с этим продуктом: Breakfast 300 г, Lunch 400 г, Dinner 300 г. Цель 2000 ккал, бюджет 14 BYN, неделя с 02.11.2026, исключений и запасов нет.

Результат: 21 запись, каждый день 2000 ккал, неделя 14 BYN, общая потребность 7000 г, покупка 14 BYN. Повторы рецептов разрешены, отсутствие запасов не мешает генерации. При B=13.9999 решение не проходит; при B=14 проходит. Это синтетическая тестовая модель, не реальный продукт и не рабочий seed.

Для проверки именно backtracking добавить альтернативный завтрак 900 ккал с повышенным приоритетом из-за наличия его ингредиентов, тогда как оставшиеся обед и ужин дают 800+600. Ветка 2300 ккал при K=2000 должна быть отклонена, затем выбран завтрак 600 ккал. В тесте проверить факт рассмотрения неудачного кандидата через диагностический счетчик/результат, не только наличие итогового плана.

### N4 Сроки годности и покупки

TimeProvider задает сегодня 02.11.2026. Партии одного продукта: 100 г со сроком 02.11 и 150 г со сроком 10.11. В меню неприготовленные записи: 80 г на 02.11 и 200 г на 03.11. Цена 0.40 BYN/100 г.

FEFO покрывает первую запись 80 г из первой партии. На 03.11 остаток 20 г первой партии непригоден. Вторая партия покрывает 150 г. Итог: потребность 280 г, пригодно распределено 230 г, **дефицит 50 г, покупка 0.20 BYN**. Простое вычитание 280−250=30 было бы ошибкой. Реальные партии после просмотра покупок остаются 100 и 150 г.

### N5 Атомарное приготовление

Для порции N2: хлопья 80 г, молоко 500 г. Подтверждение отклоняется из-за нехватки 20 г хлопьев; молоко остается 500 г, хлопья 80 г, CookedAtUtc пусто. Затем задать хлопья 300 г и молоко 1000 г: первое подтверждение оставляет 200 г/800 г и заполняет CookedAtUtc. Второе подтверждение не меняет остатки. Два конкурирующих вызова должны дать ровно один успешный расход.

| T15 | Границы 90% и 110% ккал | Равенства принимаются; значения за границей отвергаются |

| T17 | Исключение единственного ингредиента | NoCandidates без записи плана |

| T21 | Уже отмененный токен и отмена в ходе поиска | Cancelled/OperationCanceled без изменения БД |
| T22 | Перегенерация при неудаче/ошибке записи | Предыдущие план и снимки целиком сохранены |
| T23 | Изменение входных данных во время генерации | Устаревший результат не записан молча |
| T24 | Правильная ручная замена | Новый снимок и пересчет; старые другие слоты не затронуты |

| T28 | Отмена диалога приготовления | Нет записей и списания |
| T29 | Повтор и два конкурирующих приготовления | Ровно одно списание и одно CookedAtUtc |
| T30 | Искусственная ошибка сохранения при списании | После нового контекста все партии и состояние исходные |
| T31 | Будущее приготовление, новый запрет ингредиента | Отказ с понятной причиной |
| T32 | Приготовленная запись | Нельзя заменить; нельзя перегенерировать всю неделю |
| T33 | Состав Recipe изменен после планирования | Списание использует исходный снимок N2 |
| T34 | Покупки N4 | 50 г/0.20 BYN, отсутствие записи в остатки |
| T35 | В списке есть приготовленное блюдо | Его потребность не считается повторно |
| T36 | Цена каталога изменилась | Плановая цена сохранена, покупка оценивается по новой цене |
| T37 | Все продукты есть / меню не создано | Понятное пустое состояние без ложного дефицита |
| T38 | Аналитика после ручной замены и приготовления | Показатели согласованы с теми же снимками и статусами |
| T39 | Конфликт Version | Старый редактор не перезаписывает новый результат |
| T40 | Полный UI-маршрут на Windows | Вход → профиль → каталог → запасы → генерация → замена → покупки → приготовление → выход |
| T41 | Перезапуск приложения после T40 | Сохраняются пользователь, меню, запасы и приготовленные записи |
| T42 | Второй экземпляр на тот же файл | Понятный отказ, отсутствие параллельных миграций |

Не требуется один тестовый метод на каждую строку: связанные проверки можно параметризовать. Расчеты, генератор, годность, доступ, транзакции и повторное списание должны иметь автоматическое покрытие. Для T30 допустим interceptor, выбрасывающий исключение в SaveChanges после изменения отслеживаемых сущностей; проверять реальную БД новым контекстом. При использовании иного способа явно описать место отказа.

## Результаты

Для каждого сценария сохранить `ID | статус | test method или ручные шаги | фактический результат | среда | ограничение`. Полный список существующих автоматических тестов и команды запуска — в TEST_RESULTS.md. У ручной проверки указать дату и реальную Windows-среду. Если WPF не запускался, T40/T41 не обозначать успешными на основании чтения XAML.
