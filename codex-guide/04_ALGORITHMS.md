# Алгоритмы и числовой контракт

## Общие правила

Для расчета использовать исходные `decimal`, без раннего округления. КБЖУ показывать до 1–2 знаков, вес до 2, деньги до 2 с `MidpointRounding.AwayFromZero`. Суммарную стоимость округлять после суммирования точных значений, а не складывать уже округленные строки. Проверки бюджетов и диапазонов выполняются до форматирования.

### Нормы

Исходная первая процентовка задает формулу Миффлина–Сан Жеора:

```
BMR_male   = 10 * weightKg + 6.25 * heightCm - 5 * ageYears + 5
BMR_female = 10 * weightKg + 6.25 * heightCm - 5 * ageYears - 161
K = BMR * activityFactor
P_target = K * 0.30 / 4
F_target = K * 0.30 / 9
C_target = K * 0.40 / 4
```

Это учебная оценка, воспроизводящая принятую в проекте модель. Если пользователь ввел собственный суточный калораж, цели БЖУ для плана рассчитываются от этого калоража. Формула не включает цель похудения/набора и не корректируется скрыто. Для невалидного профиля вернуть ошибки ввода, а не нулевые нормы.

### Рецепт и снимки

Для каждого ингредиента с весом q граммов и значением V на 100 г:

```
ingredientValue = q / 100 * V
recipeValue = Sum(ingredientValue)
recipeCost = Sum(q / 100 * PricePer100g)
```

Формула применяется отдельно к ккал, Б, Ж, У и цене. При сохранении выбора в меню скопировать вес и все показатели ингредиентов в MenuIngredientSnapshot. Последующие расчеты плана и списание используют снимки, а не изменившийся Recipe.Ingredients.

## Автоматическая генерация

Вход: текущий UserId из сеанса, WeekStart, целевой K, бюджет B, исключения, каталог рецептов/продуктов и партии владельца. Выход: 21 предложенная запись или конкретная причина неуспеха. `MenuGenerator` не имеет доступа к БД и не изменяет реальные запасы.

Условия успешного результата:

- ровно семь дней от понедельника, в каждом Breakfast/Lunch/Dinner;
- категория рецепта соответствует слоту;
- ни один ингредиент не входит в исключения;
- `0.9*K <= calories(day) <= 1.1*K` для каждого дня включительно;
- `totalIngredientCost(week) <= B` включительно, без дополнительных 10%;
- повтор одного рецепта разрешен, разнообразие — только предпочтение;
- необязательны наличие всех ингредиентов дома и попадание БЖУ в отдельные допуски.

Бюджет означает полную стоимость всех ингредиентов меню, включая уже имеющиеся продукты. Стоимость дефицита в списке покупок — отдельный показатель. Изображение алгоритма исходника нужно уточнить в будущем отчете: бюджет недельный, а диапазон калорийности суточный.

### Порядок поиска

1. Проверить параметры, разрешенную неделю и полноту профиля/цели. Подготовить кандидатов по категориям и исключениям через LINQ. Если в категории пусто — `NoCandidates`, указать прием пищи.
2. Рассчитать КБЖУ и цену рецептов один раз на входном снимке. Слоты обходить по календарю: день 1 Breakfast, Lunch, Dinner, затем день 2 и далее.
3. Держать выбранный префикс, точную накопленную стоимость, показатели текущего дня и виртуальную копию партий. Виртуальная копия нужна только для приоритета; нехватка ингредиентов не запрещает блюдо.
4. Для очередного слота упорядочить кандидатов: выше процент обеспеченности по весу пригодными запасами на дату `max(today, slot.Date)`; затем меньше уже использований рецепта; затем ближе к доле целевых ккал для приема пищи (30/40/30%); затем дешевле; затем RecipeId. Порядок детерминированный. Уже просроченные сегодня партии не считаются доступными даже для прошедшего дня текущей недели.
5. Попробовать кандидата, добавить показатели, виртуально распределить только имеющиеся граммы FEFO. Немедленно отсечь ветку при превышении B или верхней дневной границы. На последнем слоте дня проверить также нижнюю границу. Допустимы безопасные нижние/верхние оценки по оставшимся категориям; нельзя отсекать возможное решение ошибочной эвристикой.
6. Перейти к следующему слоту. При неудаче восстановить предыдущие показатели и виртуальные партии и попробовать следующего кандидата. Это настоящий возврат по дереву решений, а не бесконечная повторная замена одного рецепта.
7. На 21-м слоте проверить весь результат повторно. Вернуть успешный набор. Если дерево исчерпано — `NoSolution`. Если исчерпан лимит — `SearchLimitReached`. Не путать эти причины.

Приоритет наличия:

```
coverage(recipe, date) =
  Sum_product(min(requiredGrams, availableSuitableGrams))
  / Sum_product(requiredGrams)
```

Перед подсчетом агрегировать потребность по ProductId. Доступность берется из оставшейся виртуальной копии партий с ExpiryDate >= date или без срока. Распределять партии по ближайшему сроку, затем Id; без срока — после датированных. Дефицит в виртуальной копии не уводит запасы ниже нуля. При откате ветки восстанавливать распределение полностью. Такая эвристика предпочитает имеющиеся продукты, но не доказывает минимальные закупки.

### Лимит и отмена

Значение по умолчанию `MaxVisitedNodes=100000`, параметр должен быть передаваемым для тестов. Один посещенный узел — одна попытка добавить кандидата; проверить лимит до очередной попытки, максимум ровно N попыток. Проверять CancellationToken на каждом шаге. Не ограничивать молча каталог первыми несколькими рецептами и затем сообщать, что решения вообще нет.

Тяжелый чистый расчет запускать вне UI-потока; отмена доступна из интерфейса. После нахождения решения, перед транзакцией записи, проверить отмену и актуальность входных данных. Сохранить MenuPlan, 21 WeeklyMenu и снимки одной транзакцией. Только после commit показать успех и обновить меню. Если запрос отменен после состоявшегося commit, интерфейс должен перечитать фактический результат, а не обещать отмену уже записанной операции.

При замене существующего плана его содержимое сохраняется до успешного commit нового. Приготовленные записи запрещают перегенерацию. Поиск не делает `SaveChanges` по одному дню.

## Ручная замена

Проверить владельца, версию плана, отсутствие CookedAtUtc, категорию и исключения. Подготовить новый снимок рецепта и новые итоги. При нарушении бюджета/калорийности вернуть запрос подтверждения с расчетами; не удерживать транзакцию на время диалога. При подтверждении повторно проверить актуальность версии/рецепта/исключений, заменить снимок в транзакции и увеличить версию. Запрет исключенного продукта не может быть обойден подтверждением. Приготовленные записи и их снимки неизменяемы.

## Приготовление и списание

1. UI показывает блюдо, дату и расход, получает подтверждение. Отрицательный ответ завершает действие без записи.
2. Сервис под общей блокировкой записи открывает контекст и транзакцию, заново проверяет сеанс, владельца, версию плана и запись. Требует CookedAtUtc == null и дату записи не позже сегодня.
3. Проверяет текущие исключения. Получает потребность из MenuIngredientSnapshot, агрегирует по ProductId. Не перечитывает новый состав рецепта для списания.
4. Для всех продуктов вычисляет распределение между пригодными сегодня партиями владельца: ближайшая годность, затем Id, без срока в конце.
5. При любой нехватке сообщает продукты и граммы дефицита, не меняя ни одной партии и признака приготовления. Просроченная партия не покрывает нехватку.
6. При полном обеспечении уменьшает все выбранные партии, устанавливает CookedAtUtc из TimeProvider, увеличивает версию плана. Нулевые партии можно сохранить; отрицательные запрещены.
7. Выполняет SaveChanges и commit. При ошибке все изменения откатываются. Повторный вызов для CookedAtUtc != null возвращает понятный отказ без нового списания.

Общая блокировка сервисов и повторные проверки защищают от двух конкурирующих команд в поддерживаемом режиме одного экземпляра. Тест должен запускать два вызова на одну запись и подтверждать ровно одно списание. Исключение на пути сохранения не должно оставлять частичный расход или приготовленную запись без расхода.

## Список покупок

Расчет относится к выбранному плану и его **неприготовленным** записям. Уже приготовленные ингредиенты не требуются повторно: их расход уже отражен в холодильнике. Запрос на построение списка не меняет БД.

1. Получить снимки неприготовленных записей и сегодняшние остатки владельца. Сортировать записи по Date, MealType, Id.
2. Для каждой записи установить дату пригодности `max(today, meal.Date)`. Из временной копии партий распределить продукты FEFO только при сроке не раньше этой даты. Одни и те же граммы использовать один раз.
3. Непокрытые граммы суммировать по ProductId; нулевой дефицит не выводить. Требуемое/покрытое/дефицит показать отдельно.
4. Для оценки покупки брать **текущую** цену Product.PricePer100g: `missingGrams/100*currentPrice`. Группировать по текущей категории продукта, внутри по имени. Отобразить дату расчета и итог.

Простое `Sum(allRequirements)-Sum(allStocks)` неверно при разных сроках годности: сначала требуется распределение по датам. Проверить сценарий, где весь запас истекает до запланированного ужина. Список не резервирует товары для других недель и не добавляет продукты в холодильник автоматически.

## Аналитика

Из снимков считать плановые КБЖУ по дню и неделе, отклонение калорий от сохраненной цели, БЖУ от сохраненных целей, полную стоимость меню и остаток `B-menuCost`. Из расчета покупок отдельно показывать стоимость дефицита по текущим ценам. При ручном превышении остаток бюджета может быть отрицательным с видимым предупреждением.

Показывать число приготовленных записей и сумму КБЖУ подтвержденных блюд в выбранном плане. Это учет подтверждений, а не независимо измеренное физиологическое потребление. Даты фактических подтверждений можно показать отдельно; не относить позднее приготовление к дате плана как к доказанному фактическому дню питания. БЖУ выражаются и граммами, и отклонением от целевых граммов. Не вводить скрытые коэффициенты и не обещать математически оптимальный рацион.
