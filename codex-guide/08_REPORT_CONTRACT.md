# Контракт соответствия отчета коду

Финальный Word-отчет будет подготовлен после проверки публичной репозиторийной версии. Сейчас Codex создает доказательную документацию, по которой можно восстановить реализацию. Предложенные в гайде имена не являются доказательством существования классов.

## Обязательные материалы в репозитории

Создать `docs/report/` и заполнить файлы по фактам:

| Файл | Что должно быть внутри |
| --- | --- |
| `IMPLEMENTATION.md` | Связное описание реальной физической структуры и модулей, без неподтвержденных возможностей |
| `CODE_MAP.md` | Требование Rxx → проект/относительный путь → тип и метод → экран/команда → тест/проверка |
| `DATABASE.md` | Все настоящие таблицы, столбцы и SQLite-типы, масштабы INTEGER, PK/FK/индексы/CHECK, delete behavior, миграции |
| `ALGORITHMS.md` | Входы, порядок действий, условия, формулы, ошибки, границы транзакций и реальные методы |
| `TEST_RESULTS.md` | Фактические команды, среда, результаты автоматических и ручных проверок T01–T42, ограничения |
| `VERSIONS.md` | TargetFramework, SDK, язык, пакеты с номерами, версия SQLite-runtime при доступности, Windows/VS если проверены |
| `DECISIONS.md` | Отличия от первой работы и гайда, причина, место в коде, необходимые правки текста |
| `LIMITATIONS.md` | Что реализовано с ограничениями, что не выполнено/не проверено, влияние на демонстрацию |
| `HANDOFF.md` | Итоговая передача по 09_HANDOFF_TEMPLATE.md |

Кроме этих файлов: README с чистой установкой и запуском, `docs/diagrams/` с исходниками актуальных схем, при доступной Windows-проверке — реальные демонстрационные скриншоты в `docs/screenshots/` без личных данных. Не создавать фиктивные скриншоты, логи, файлы результатов или номера коммитов.

## Матрица реализации

Строки R01–R16 обязательны. Для каждого требования записать точный путь и символ. Если функция распределена по нескольким типам — перечислить действительно важные переходы. Допустимы ссылки на номера строк, но устойчивой опорой остаются путь и имя символа. Все пути должны существовать, имена методов — находиться в указанных файлах.

Шаблон строки, который требуется заполнить реальными значениями:

```
R11 | <путь сервиса> | <тип>.<метод> |
<ViewModel>.<команда> | T27/T29/T30/T33 | <реальные test methods> | <статус>
```

Не оставлять угловые скобки и пустые «реализовано» в готовой передаче. Неподдержанный сценарий явно отмечать `NotImplemented`, непроверенный `NotRun/Blocked`.

## Содержание будущего раздела 3

### 3.1 Физическая структура

Описать фактические solution и проекты, зависимости, папки, точку запуска и связывание сервисов с ViewModels. Затем — физическую БД: сущности/таблицы, типы и масштабирование, ключи и ограничения, жизненный цикл контекста, путь файла и миграции. Разделить требования сервисов и гарантии БД: наличие 21 записи обычно не обеспечивается одним внешним ключом.

Показать создание БД при первом запуске, seed, авторизацию, переключение экрана и завершение приложения. Только если соответствующий механизм действительно есть, описывать блокировку экземпляра, ревизии и версионность. Не копировать из примера Гульченко резервное копирование, 30-секундный таймер, Serializable, конкретный PasswordHasher iteration count и другие особенности без наличия аналогичного кода.

### 3.2 Описание разработанных модулей

Для каждого модуля дать назначение, реальные классы и ключевые методы, входы/выходы, проверки и сохранение результата. Обязательны: доступ/профиль, каталоги и расчет рецепта, учет партий, генератор меню, ручная корректировка, приготовление, покупки, аналитика, связь UI и обработка ошибок.

Для главных операций показать сквозной маршрут: XAML-команда → ViewModel → сервис → расчет/DbContext → транзакция → обновление UI. Указать, где проверяется владелец, где исключения превращаются в сообщения и на каком шаге данные уже зафиксированы. В алгоритме приготовления явно показать проверку повторного списания и проверку всех продуктов до расхода.

Сведения о проверках в этом материале нужны для достоверности. Оформление итоговых разделов 4 и 5 выполняется отдельно по объему следующего запроса; не выдавать их за уже согласованный Word-текст.

## Схемы

Подготовить исходники Mermaid или PlantUML, чтобы их можно было перерисовать для Word без угадывания:

1. Зависимости проектов и основных слоев.
2. Диаграмма классов предметной области с кратностями и техническими дополнениями.
3. Физическая схема БД с реальными именами таблиц и ключей.
4. Варианты использования пользователя, соответствующие работающим экранам.
5. Блок-схема генерации с конечным поиском, отказом/отменой и атомарным сохранением.
6. Блок-схема приготовления с FEFO, нехваткой, отказом и commit.
7. Блок-схема списка покупок с учетом сроков и неприготовленных записей.

Бланк требует диаграмму классов и use-case. Остальные схемы — материалы для описания реализации по примеру Гульченко. Не проставлять окончательные номера рисунков до интеграции в записку. Схемы должны повторять фактический код, включая ошибки и выходы, а не только идеальный путь.

## Что исправить в исходном Word позже

Сохранить автора Стреху, тему домашнего меню, преподавателя Усенко Ф. В. и исходные реквизиты, если владелец не дает обновления. В бланке присутствует остаточная подпись «С. П. Иванов» — это шаблонный конфликт, его нельзя переносить как имя автора. Точный финальный титул и подписи проверить отдельно, не изобретать группу или шифр проекта.

Сопоставить правки из 01_CONTEXT.md с готовым кодом: SQLite без сервера, текущие версии пакетов, формула и профиль, стоимость меню/закупок, калорийность и БЖУ, расширенные сущности, исключения и права, выходы алгоритма и снимки. Добавить отсутствующую полноценную диаграмму классов. Исходную use-case и блок-схему генератора обновить, если фактические сценарии изменились.

Наличие упоминания СТП 01–2024 в исходных документах не означает, что полный стандарт приложен. Не выдумывать точные требования к полям, шрифтам и нумерации как цитату из стандарта. При подготовке Word использовать предоставленный образец как ориентир и отдельно проверить доступный текст стандарта. Сейчас кодовому агенту не нужно редактировать Word или подтверждать соответствие оформления стандарту.

## Перед окончанием

- Сверить R01–R16 с исходниками и тестами; проверить все пути и символы CODE_MAP.
- Сверить DATABASE с миграцией InitialCreate и model snapshot, включая масштабы и каскады.
- Сверить формулы и лимиты ALGORITHMS с кодом, UI и числовыми тестами.
- Убедиться, что все показанные UI-действия вызывают реальные сервисы.
- Убрать вымышленные результаты, обещания глобальной оптимальности и медицинской точности.
- Указать состояние git: ветка, фактический HEAD, наличие локальных изменений. После публикации сверять согласуемый отчет с конкретным commit SHA.

Если документация меняется отдельным коммитом после кода, разрешено записать SHA проверенного кода и SHA итоговой ветки отдельно. Не пытаться вписать коммиту его собственный будущий хеш. Пока коммита нет, указывать это честно, а не придумывать SHA.
