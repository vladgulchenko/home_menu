# Контекст и границы этапа

## Что передано

1. Бланк задания Стрехи: тема, обязательные C#, Visual Studio 2022, WPF, ООП, классы, база данных; требования к чистоте кода и оформлению записки по СТП 01–2024. Обязательная графика — диаграмма классов и диаграмма вариантов использования.
2. Первая процентовка Стрехи: введение, разделы 1–2, информационная база, функции, алгоритм генерации, сущности, стек. Это основной предметный источник.
3. Вторая процентовка Гульченко: приложение учета заказов ПВЗ. Используется как пример того, как описывать физическую структуру, реальные сервисы и алгоритмы, подтвержденные кодом. Заказы, сотрудники, роли оператора и администратора, возвраты и статусы ПВЗ к HomeMenu не относятся.

В календарном плане задания: разделы 1–2 — 15.10.2026, 30%; раздел 3 — 15.11.2026, 20%; раздел 4 — 15.12.2026, 50%; срок завершения — 24.12.2026. Слова «вторая/третья процентовка» в переписке неоднозначны. В текущем комплекте реализуется программа для последующего написания **раздела 3 «Программная реализация»**, включая необходимую основу тестирования. Word будет оформлен после получения публичного репозитория.

По бланку раздел 3 содержит 3.1 «Физическая структура» и 3.2 «Описание разработанных модулей». Разделы 4 «Тестирование» и 5 «Применение программы» не подменяют этот раздел; материалы для них можно собирать заранее.

## Обязательные возможности из первой работы

Локальная авторизация, личный профиль и расчет норм, справочники продуктов и рецептов с изменением данных и поиском, учет партий продуктов и сроков годности, генерация семидневного меню по калорийности, бюджету и исключениям, преимущество имеющихся ингредиентов, возврат к альтернативам при неудачном подборе, ручная замена блюд, списание при подтверждении приготовления, список дефицитных продуктов, финансовая и пищевая аналитика. Автономная работа после установки. Пользователь приложения один тип роли, учетных записей может быть несколько.

## Проектные уточнения и будущие правки записки

Эти решения приняты в гайде для однозначной реализации. Они не выдаются за цитаты из исходников.

| Тема | Решение | Что уточнить в разделах 1–2 |
| --- | --- | --- |
| Единицы | Все ингредиенты и остатки в граммах; питание и цена за 100 г; BYN | Исключить обещание произвольных единиц без конвертации |
| Размер рецепта | Рецепт описывает одну порцию; три приема пищи в день, один человек | Указать масштаб планирования; семейные порции не реализуются |
| Бюджет | Жесткий предел полной расчетной стоимости недельного меню | Удалить неясный допуск 10% к бюджету; различать стоимость меню и закупки |
| Калорийность | Каждый день в пределах 90–110% заданной цели | Уточнить нижнюю границу, а не только запрет превышения |
| БЖУ | Цели 30/30/40% рассчитываются и сравниваются с планом; строгого фильтра по каждому макронутриенту нет | На схеме заменить неоднозначное «лимит КБЖУ» на конкретную проверку калорийности; не обещать оптимум по БЖУ |
| Поиск меню | Детерминированный ограниченный backtracking, отказ без записи при неудаче | Добавить выходы «нет решения», «исчерпан лимит», «отмена» |
| БД | Встроенный файл SQLite и миграции EF Core | Исправить «соединение с сервером СУБД»: отдельного сервера нет |
| Каталоги | Продукты и рецепты общие для локальной установки; профиль, запасы, исключения и планы принадлежат пользователю | Не утверждать, что общие каталоги изолированы по пользователям |
| История | Снимки ингредиентов и цен в запланированных приемах пищи | Добавить технические сущности MenuPlan, MenuIngredientSnapshot и UserExcludedProduct |
| Списание | Подтверждение до транзакции, при нехватке полный отказ; повтор запрещен | Заменить неясное «откат при отмене» точным порядком действий |
| Статистика | Плановая стоимость/КБЖУ и учет подтвержденных приемов; без банковских/магазинных данных | Не называть оценку закупок реальными расходами |
| Хеш пароля | Библиотечная проверка хеша с солью | Не описывать простое сравнение двух хешей произвольной функцией |
| Обоснование стека | Сохраняется выбранная .NET 8; точные версии из итогового проекта | Не копировать без проверки слово «актуальная» и обещания поддержки из старого текста |

Указанные уточнения входят в текущий контракт реализации. При необходимости другого решения Codex должен явно записать изменение, его причину и влияние на текст, схему, тесты и интерфейс. Запрещено молча менять обязательные функции. Нельзя гарантировать отсутствие расхождений до проверки настоящего кода: согласование выполняется по конкретному commit SHA.

## Вне объема

Интеграции магазинов и доставки, платежи, нейросети, лечебные диеты, медицинские рекомендации, облачная синхронизация, мобильный клиент, роли ПВЗ. Слово «интеллектуальный» из исходного текста не означает применение ML: реализуется обычный алгоритм поиска с эвристическим порядком кандидатов.
